# UII Content Console — workflow, architecture and acceptance

Status: **feature code / preview**, not proof of deployment to the current Render API.
Canonical review branch: `feat/guided-dschool-learning-path-20261121`.
UX blueprint in Canva: https://www.canva.com/d/aI99SuR9Wk0LVxJ

## As-is evidence

- `/learn` had a lecturer-only creation form and a lesson editor near student learning content. The course overview showed computed lesson duration, but the duration field was not exposed in the authoring form.
- `/notifications` listed personalized notices and permitted marking them as read. No editor API existed for lecturers to compose notifications; automatic deadline reminders were generated by a scheduled backend job.
- `/community` exposed `POST /community/posts` for approved projects; however there was no explicit UI step to approve the entire project for showcase after rubric review of an individual `SubmissionSnapshot`. Assessing a snapshot does not change `Project.status`.
- The two example groups on Community are illustrative only, not LMS-backed groups or shared projects.

## Proposed and coded to-be workflow

### A. Lecturer course authoring

1. Lecturer or administrator signs in; server reads effective role from `/auth/me`.
2. Console `/console` lists only manageable courses (lecturer owns course; admin sees all).
3. Create draft or edit title, description, level and status using existing `POST /courses`, `PUT /courses/:id`.
4. Select a lesson; edit title, description, order, content type, linked video, textual content, publish state and **durationMinutes** with `PUT /lessons/:id`. New lessons use `POST /courses/:id/lessons`.
5. Course overview duration = sum of durations of lessons visible to the viewer. This avoids contradictory manual totals. Student-visible time may differ from lecturer total if lessons are still draft.
6. Preview with `/learn?course=:id`; explicitly publish the course when ready.

No new course-duration database field is required.

### B. Notification composition

1. Lecturer selects own course, title, body and recipients from enrolled students; administrator may select all students.
2. API `POST /notifications/announcements` is protected by authenticated JWT and server-side course ownership checks. A unique publication identifier is generated per submission, and one notification row is created per distinct recipient.
3. Inbox `/notifications` displays the content with line breaks and links back to course or dashboard. The composer displays the actual recipient count after the write succeeds.
4. Current scope = **immediate in-app announcement only**. Email, SMS, scheduled posts, persistent drafts, approvals and campaigns are not claimed. A Vercel preview with an older Render backend may return 404 because the endpoint is not deployed.

### C. Academic review → optional project showcase

1. Learners create groups/projects, practice in five **non-linear** modes and attach versioned private evidence.
2. Learners submit a snapshot, lecturer uses Review/rubric. This decision applies to that immutable submission, not to publication consent.
3. Lecturer opens Console → Project Showcase and approves **the whole project** with `POST /projects/:id/approve-showcase`; backend requires at least one approved submission snapshot and lecturer ownership/admin permission.
4. This sets `Project.status = APPROVED` and creates a private in-app notice for owner/team members; it does **not** create a public Post.
5. **Project owner only** opens Community and publishes a caption using `POST /community/posts`. The backend verifies ownership and project approval; creating the post changes project status to `PUBLISHED`.
6. Demo groups never produce real Posts; sensitive private evidence is not automatically attached to public content.

### D. Student journey

Discover → Enroll → Learn → Practice → Apply in Studio → Save evidence →
Submit snapshot → Get rubric feedback → Improve → Optional owner-controlled showcase.

## System architecture

`UII Next.js` (WorkspaceNav / Content Console / Course Player / Review / Community)
→ same-origin `/backend/*` reverse proxy → `NestJS on Render` with authenticated
controllers, guards and per-resource permissions → `Supabase Auth`, PostgreSQL
via Prisma, private object storage. Admin and lecturer capabilities are never
granted based solely on frontend state or user-editable metadata.

## Release gates

- [ ] Build and CI pass on the **final** commit (Frontend, Backend, Playwright).
- [ ] Staging Render API includes the new Console announcement and showcase-approval endpoints.
- [ ] Community Q&A migration is applied to the staging DB and Prisma history reconciled.
- [ ] Create/edit course and duration while authenticated as lecturer; verify that only published lessons affect student-visible duration.
- [ ] Lecturer announcement arrives exactly once per enrolled student; unrelated courses and students cannot receive it.
- [ ] Student and unrelated lecturer cannot send announcements.
- [ ] Rubric approval alone does not publish project. Whole-project approval requires approved snapshot and course lecturer/admin authority.
- [ ] Owner opts into publication; administrators cannot silently publish student work. Preserve evidence privacy.
- [ ] Accessible mobile forms, keyboard navigation, clear success/error, no demo content masquerading as real.
- [ ] Authenticated staging smoke and user acceptance before merging `main` or moving stable alias.

## Design rationale

- **Discoverability**: a labeled, role-specific Console is simpler than hiding authoring inside the learner's page.
- **Single source of truth**: time estimates are derived from lesson durations; fewer conflicting fields.
- **Separation of concerns**: learning, editing, communication, assessment and publishing each have one recognizable place.
- **Reversibility**: Save Draft, Preview, and Publish reduce accidental disclosure.
- **Consent and least privilege**: academic evaluation and public publication are independent.
- **Feedback visibility**: show actual save/recipient counts and explicit API failure; never invent success.
